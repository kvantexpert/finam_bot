# Finam Bot — описание проекта

## 1. Что это за проект

`finam_bot` — Python-проект для работы с API брокера Финам и построения автоматизированной торговой инфраструктуры вокруг рыночных данных.

Исторически проект начинался как набор скриптов для:

- получения котировок;
- мониторинга валют;
- поиска треугольных арбитражных возможностей;
- расчёта потенциальной доходности;
- отправки торговых заявок.

Сейчас проект переводится из набора связанных скриптов в нормальную модульную архитектуру.

## 2. Что хотим получить

Целевая система должна разделять:

1. получение рыночных данных;
2. нормализацию рыночных моделей;
3. стратегию и поиск возможностей;
4. проверки риска;
5. построение плана заявок;
6. исполнение;
7. контроль фактических fills;
8. reconciliation позиций;
9. безопасное закрытие/unwind;
10. мониторинг и диагностику.

Главный принцип: **сигнал стратегии не должен напрямую управлять реальным счётом**.

## 3. Почему проект сейчас реструктурируется

Старый код вырос постепенно и содержит несколько параллельных реализаций одних и тех же задач. В результате:

- есть дублирование арбитражного кода;
- рыночные модели смешаны с FinamPy protobuf-моделями;
- стратегия, риск и исполнение находятся слишком близко друг к другу;
- legacy-код предполагает конкретные размеры тика и лотов;
- нет полноценного контроля partial fills;
- нет надёжной reconciliation фактических позиций;
- исторический `CancelOrder` использовался как способ закрытия уже исполненной позиции;
- существующий live-контур нельзя считать безопасным для реального счёта.

Поэтому сначала выполняется структурная миграция, а затем отдельно исправляется торговая модель.

- `execution/`;
- `monitoring/`.

### Application boundary

Создан `src/finam_bot/app.py` и новая точка входа арбитражного приложения.

`run_arbitrage.py` теперь является переходной compatibility-обёрткой, а не местом реализации торговой логики.

### Безопасность execution

Новый execution engine пока отключён. Попытка выполнить торговый запуск должна завершаться безопасно, пока не реализованы risk/fill/reconciliation/unwind.

### Legacy

`core/` заморожен. Он не удалён, потому что старый `currency_monitor_cli.py` и другие legacy entrypoints ещё зависят от него.

## 5. Что сейчас нельзя считать готовым

Не считать готовыми для реальной торговли:

- старый `arbitrage_trader.py`;
- старый `arbitrage_finder.py`;
- `core/arb_executor.py`;
- старую модель треугольников;
- исторические расчёты лотов;
- автоматическое выполнение заявок.

## 6. Главные технические задачи

### Рыночная модель

Нужно получить реальный список доступных инструментов Finam и определить для каждого:

- валютную пару;
- направление котировки;
- tick size;
- decimal precision;
- lot size;
- торговую площадку;
- доступность market/limit orders.

После этого строить арбитражные циклы только из реально существующих отношений.

### Strategy

Стратегия должна возвращать структурированный сигнал/Opportunity, но не размещать заявки самостоятельно.

### Risk

Перед заявкой должны проверяться:

- допустимый объём;
- максимальная экспозиция;
- количество одновременно открытых циклов;
- дневной убыток;
- свежесть котировок;
- допустимое проскальзывание;
- состояние счёта.

### Execution

Execution должен понимать состояние каждой ноги:

```text
planned → submitted → partially_filled → filled / failed
```

Нельзя считать заявку исполненной только потому, что запрос на её размещение успешно отправлен.

### Reconciliation

После каждого торгового действия необходимо сравнивать ожидаемое состояние с фактическими позициями/остатками брокера.

### Unwind

Если треугольник исполнен не полностью, система должна иметь отдельный безопасный сценарий выхода из фактически возникшей позиции.

## 7. Правила работы с проектом

- Сначала аудит, потом изменение.
- Структурные изменения не смешивать с изменениями торговой логики.
- Не удалять legacy-файл, пока не проверены его зависимости.
- Не переносить старую торговую математику автоматически только потому, что она уже работает.
- Не считать `CancelOrder` эквивалентом закрытия позиции.
- Не включать live execution до появления полноценного risk/fill/reconciliation слоя.
- Не хранить токены, ключи, логи и runtime-данные в Git.

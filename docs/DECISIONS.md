# Архитектурные решения Finam Bot

Этот файл нужен не для описания каждого коммита, а для фиксации решений, которые через месяц могут быть непонятны без контекста.

## ADR-001 — новый код находится в `src/finam_bot/`

**Решение:** собственный код постепенно переносится в пакет `src/finam_bot/`.

**Почему:** старый repository layout смешивал domain-код, CLI, конфигурацию, SDK и runtime-файлы.

**Следствие:** новые модули не добавлять в `core/`, если только это не временная поддержка legacy-кода.

## ADR-002 — `core/` временно заморожен

**Решение:** `core/` не удаляется сразу.

**Почему:** старые entrypoints всё ещё напрямую используют его. Массовое удаление сломает проект и усложнит разбор причин.

**Следствие:** сначала миграция entrypoint, затем проверка зависимостей, затем удаление конкретных legacy-файлов.

## ADR-003 — `run_arbitrage.py` остаётся compatibility entrypoint

**Решение:** root-level `run_arbitrage.py` не содержит торговую реализацию.

**Почему:** внешний способ запуска можно сохранить, одновременно перенося приложение в `src/finam_bot/app.py`.

**Следствие:** основная логика не должна возвращаться в этот wrapper.

## ADR-004 — live execution отключён во время миграции

**Решение:** новый `Executor` пока выбрасывает безопасную ошибку вместо размещения заявок.

**Почему:** структурная миграция не должна случайно превратиться в запуск непроверенной торговой системы.

**Следствие:** paper/live режимы появятся только после risk, fill control, reconciliation и unwind.

## ADR-005 — FinamPy не должен протекать в domain layer

**Решение:** API adapter преобразует внешние объекты в собственные модели приложения.

**Почему:** стратегия и риск не должны зависеть от protobuf/API-деталей SDK.

**Следствие:** изменение SDK не должно требовать переписывать strategy/risk.

## ADR-006 — старые `0.0001` и magic lot coefficients не переносим автоматически

**Решение:** исторические расчёты тика и лотов не считаются корректной частью новой модели.

**Почему:** реальный инструмент может иметь другой tick size, precision и lot size.

**Следствие:** перед новой strategy нужно исследовать фактические инструменты Finam.

## ADR-007 — `CancelOrder` не является unwind

**Решение:** отмена заявки и закрытие уже возникшей позиции — разные операции.

**Почему:** после исполнения заявки отменять уже нечего; требуется отдельная противоположная операция с контролем результата.

**Следствие:** новый execution должен моделировать order state и фактические fills.

## ADR-008 — сначала структурная миграция, потом изменение торговой математики

**Решение:** не смешивать cleanup/refactor с исправлением стратегии в одном изменении.

**Почему:** иначе невозможно понять, что именно изменило поведение системы.

**Следствие:** коммиты и этапы должны быть небольшими и тематическими.

## ADR-009 — арбитражный цикл строится только из реального market universe

**Решение:** новая triangle/cycle model не переносит старый список комбинаций автоматически.

**Почему:** историческая конфигурация содержит отношения, которые не подтверждены фактическим набором доступных инструментов.

**Следствие:** сначала inventory инструментов, затем граф рынка, затем поиск циклов.

## ADR-010 — сначала фактическое состояние, потом автоматизация

**Решение:** при каждом крупном изменении сначала проверять существующие зависимости и runtime-поведение.

**Почему:** проект содержит legacy-слой и несколько старых entrypoints; предположения легко приводят к скрытым поломкам.

**Следствие:** стандартный порядок работы: аудит → минимальное изменение → smoke-test → отдельный коммит → следующий этап.
